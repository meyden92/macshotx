# Liquid Glass is the only chrome style, hosted inside the overlay

Every overlay chrome surface — toolbar strip, tool-options row, resolution box, helper and hint cards, tooltips, the multi-select delete affordance and the post-processing panels — is built through `GlassChrome` (`GlassChrome.swift`) and rendered with the system's Liquid Glass material. The surfaces stay exactly where they were in the capture overlay's own view hierarchy (Plan A), so hit-testing, event routing, first responder handling, cursor management and phase 3's collision-avoidance layout are untouched.

## Considered Options

- **A theme toggle or a "classic chrome" mode** — rejected, not deferred. The app's floor is macOS 26, so the material is unconditionally available and there is nothing to feature-detect. A second visual mode doubles the surface area that has to keep looking right, for no user benefit.
- **A hand-rolled opaque fallback** — rejected. Reduce Transparency is answered with the system's own reduced material (`NSVisualEffectView`), chosen by a pure function of the accessibility flags, never a hand-mixed colour.
- **Hosting each chrome cluster in its own borderless non-activating child panel (Plan B)** — specified up front as the fallback if in-window content turns out not to be sampled, or if the backdrop renders stale in a borderless, transparent, high-window-level window. Not implemented: it costs re-established tracking areas, view-to-screen geometry and a keyboard-focus rule, and Plan A is the option that keeps this phase a restyle rather than a rearchitecture.

## Consequences

- Chrome colours are dynamic system colours resolved at draw time. The accent roles read `controlAccentColor`, so the active tool and the primary action are in *the user's* colour. Nothing is snapshotted into a layer at construction. The boundary is deliberate: annotation colours are user data, are persisted as hex, and are untouched by this rule.
- The kit offers two placements. `surface(_:radius:tint:)` wraps a view as the glass view's own `contentView`, which is the only placement the platform makes z-order and legibility guarantees for, and is used wherever a surface owns its content outright. `installBackdrop(in:)` puts the same material *behind* a view that owns its own children, as a sibling ordered below them — AppKit guarantees sibling z-order, and this is what lets the toolbar strip, the colour picker and the presets panel keep the child structure their behaviour and their tests are written against. Restructuring those hierarchies would have made the phase a rearchitecture, which is exactly what it is not.
- Adjacent surfaces are not merged into a shared `NSGlassEffectContainerView` across the overlay, because a container only groups its own descendants and the chrome surfaces are siblings of the overlay by design. Within the toolbar, the strip and its tool-options row are one glass surface, which is the same win: one sampling region, one pass.
- **Not verified on real hardware.** The ticket asks for a direct observation that the glass backdrop shows the frozen screenshot and updates live rather than showing a stale cached backdrop — the known platform risk for borderless transparent windows at elevated levels. That observation has not been made. If it turns out to be wrong, the reversal is Plan B above, and the geometry it needs is already shared.
